# 飞牛 NAS 上 OpenClaw 安全加固与公网访问教程
> 适用于：希望在飞牛 NAS（fnOS）上让 OpenClaw 更安全、并支持公网访问的用户

---

## 这篇教程解决什么问题

很多人把 OpenClaw 部署到飞牛 NAS 之后，第一反应是：

- 先让它跑起来
- 再想办法远程访问

但真正危险的地方也就在这里：

- 端口直接暴露到公网
- 控制面没有额外保护
- Token 太弱或泄露
- 设备认证被关闭
- 回调地址直接裸露
- 多通道接入后权限边界不清

这篇教程要做的，就是告诉你：

1. 如何让 OpenClaw **更安全**
2. 如何在需要时 **正确地开放公网访问**

---

## 一个最重要的原则

如果你只记住一句话，请记住这个：

> **能不直接暴露 OpenClaw 原始端口，就尽量不要直接暴露。**

推荐顺序永远是：

1. 先内网运行
2. 再用反向代理 / 网关统一暴露
3. 再配鉴权、白名单、HTTPS、回调策略

而不是：

- 直接把 `18789` 映射到公网然后开用

---

## 一、先理解 OpenClaw 哪些面是敏感的

一个部署好的 OpenClaw，通常至少包含这些部分：

- **主网关端口**（如 `18789`）
- **浏览器控制端口**（如 `18791`）
- **控制 UI**
- **消息通道回调入口**（如飞书 / QQ 等）
- **认证文件**（如 `auth-profiles.json`）

这些里最危险的通常是：

### 1. 网关端口

如果网关直接暴露，别人拿到 token 就能调用你的 OpenClaw。

### 2. 浏览器控制端口

如果浏览器控制服务也暴露出去，风险更大，因为这相当于给了别人一只“远程手”。

### 3. 认证文件

`auth-profiles.json` 里通常存着模型 provider 的认证信息，泄露后后果很直接：

- 别人能用你的 API key
- 账单可能直接飞起

---

## 二、第一层安全：先把配置收紧

### 检查这些危险配置

很多初学者为了方便，会打开一些危险选项，例如：

```json
"allowInsecureAuth": true,
"dangerouslyDisableDeviceAuth": true
```

如果你看到类似配置，说明目前是“方便优先”，不是“安全优先”。

### 建议做法

把这类配置尽量改成：

```json
"allowInsecureAuth": false,
"dangerouslyDisableDeviceAuth": false
```

如果你的当前环境必须临时开着，那也建议：

- 只在内网用
- 不要裸露到公网
- 尽快做二层防护（反代、鉴权、白名单）

---

## 三、第二层安全：不要直接裸露容器端口

很多人习惯直接这样映射：

```bash
-p 18789:18789
-p 18791:18791
```

这在内网测试可以，但如果你做了公网端口映射，就等于把 OpenClaw 的控制能力直接暴露出去。

### 更推荐的方式

#### 方案 A：只监听本机 / 内网

例如只绑定局域网，或者只让反向代理访问。

#### 方案 B：通过 Nginx / Caddy 暴露

让外部访问先经过：

- HTTPS
- 域名
- Basic Auth / Token 校验
- IP 白名单
- 路径控制

这样安全性会高很多。

---

## 四、第三层安全：把公网入口和内部服务分开

推荐结构：

```text
公网用户
   ↓
Nginx / Caddy / Cloudflare Tunnel
   ↓
OpenClaw 网关
```

这样做的好处：

- OpenClaw 原始端口不直接暴露
- TLS / HTTPS 统一处理
- 可以加额外鉴权
- 可以做访问日志
- 可以单独限制回调路径

---

## 五、什么时候必须开放公网访问

不是所有场景都需要公网。

### 只在这些情况开放公网才比较合理：

- 你要远程访问 OpenClaw Web 界面
- 你要接入飞书 / QQ 机器人等需要公网回调的平台
- 你要从外网调用 OpenClaw API

如果你只是：

- 在局域网里自己用
- 本地 NAS 自己对话
- 做内网 Agent

那就尽量不要开公网。

---

## 六、公网访问推荐方案

### 方案 1：域名 + HTTPS + 反向代理（推荐）

推荐程度最高。

流程：

1. 准备一个域名
2. 解析到你的公网 IP
3. 用 Nginx / Caddy 反代到 OpenClaw
4. 配 HTTPS 证书
5. 限制访问策略

优点：

- 最正规
- 最稳定
- 最适合长期使用

---

### 方案 2：Cloudflare Tunnel

如果你不想自己折腾端口转发、证书、NAT，也可以考虑 Tunnel 类方案。

优点：

- 不必直接开放源站端口
- HTTPS 方便
- 暴露面更小

缺点：

- 多一层外部依赖
- 部分平台回调兼容性需要测试

---

### 方案 3：直接端口映射（不推荐长期使用）

只有在临时测试时才勉强能接受。

如果你真的这么做，至少要：

- 确保 token 足够强
- 关闭不安全认证
- 不暴露浏览器控制端口
- 有额外的网络层限制

---

## 七、浏览器控制端口特别危险

很多人关注 `18789`，却忽略了 `18791`。

### 这个端口为什么危险

因为它对应的是浏览器控制服务。

如果直接暴露，风险比普通 API 更高。简单理解就是：

- 网关泄露 → 可能被调用模型 / 消耗额度
- 浏览器控制泄露 → 可能被远程操控页面

### 建议

- **不要把 `18791` 直接暴露到公网**
- 只保留本地 / 内网访问
- 如果确实要远程使用，也尽量走可信代理和额外鉴权

---

## 八、消息通道公网回调怎么做更安全

像：

- 飞书
- QQ 机器人
- Telegram（部分场景）

这些通道可能涉及公网入口。

### 推荐思路

不要把整个 OpenClaw 都暴露出去，而是：

- 仅暴露必要的回调路径
- 不把调试面板、浏览器控制、其他敏感接口一起开放
- 用 Nginx 分路径反代

例如：

```text
https://your-domain.com/feishu
https://your-domain.com/qqbot
```

只开放这些必要入口，而不是把所有能力一起开放。

---

## 九、认证文件怎么保护

### 高风险文件

```bash
/vol1/1000/openclaw/agents/main/agent/auth-profiles.json
```

这个文件通常包含：

- 模型 provider 密钥
- 认证信息

### 建议

- 不要截图发群
- 不要提交进 Git 仓库
- 不要放在公开共享目录
- 定期备份，但备份也要注意权限

如果你怀疑泄露了：

1. 立刻更换 provider key
2. 更新 auth 文件
3. 重启服务

---

## 十、最小安全建议清单

如果你不想一开始就做得太复杂，至少先做到这几条：

### 必做

- [ ] 不直接暴露 `18791`
- [ ] 网关 token 使用强随机值
- [ ] 关闭不安全认证选项
- [ ] 不把 `auth-profiles.json` 外泄
- [ ] 容器只挂载必要目录
- [ ] 日志里不要随意暴露密钥

### 推荐做

- [ ] 通过域名 + HTTPS 暴露
- [ ] 加一层反向代理
- [ ] 加访问白名单
- [ ] 回调路径最小化暴露
- [ ] 给公网入口单独做访问策略

---

## 十一、如果一定要公网访问，推荐的最小结构

推荐结构：

```text
公网
  ↓
域名 + HTTPS
  ↓
Nginx / Caddy
  ↓
OpenClaw 18789（内网）
```

并且：

- `18791` 不对公网开放
- 只开放必要路径
- 敏感管理接口不要全部透出

---

## 十二、常见危险误区

### 1. 为了方便，把危险选项全开

短期是省事，长期是埋雷。

### 2. 为了公网访问，直接映射全部端口

尤其是把浏览器控制也映射出去，这是高风险操作。

### 3. 把 token 当成密码但长期不换

建议定期轮换。

### 4. 把认证文件当普通配置文件随便传

这往往比暴露端口还危险。

### 5. 为了接 QQ / 飞书，把整个网关都暴露出去

实际上通常只需要有限的回调入口。

---

## 十三、推荐上线顺序

如果你想把 OpenClaw 从“内网测试”升级到“公网可用”，建议顺序是：

### 第 1 步：先保证内网稳定

先把：

- 模型
- 搜索
- Ollama
- 多通道

都在内网跑稳。

### 第 2 步：再做域名与 HTTPS

### 第 3 步：再做回调入口

### 第 4 步：最后才考虑开放外部 API 或 UI

这样风险最可控。

---

## 十四、最实用的一条建议

如果你现在问：

> “我到底该不该把 OpenClaw 直接暴露公网？”

我的建议是：

- **如果只是自己用，尽量不要直接暴露原始端口**
- **如果确实要远程访问，就一定加反向代理、HTTPS、鉴权和最小暴露策略**

---

## 总结

飞牛 NAS 上 OpenClaw 的安全加固，重点不在于“多装几个安全工具”，而在于控制暴露面：

- 不必要的端口不暴露
- 不必要的路径不暴露
- 不安全的认证不开
- 不该外泄的认证文件不外泄

一句话总结：

> **真正安全的公网访问，不是“能从外面打开”，而是“只暴露必要能力，其余全部留在内网”。**
